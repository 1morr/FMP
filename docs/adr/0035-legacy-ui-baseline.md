# 0035 — UI 以舊版為底：六項導覽含佇列、舊版播放頁與播放列、舊版主題與外觀設定、自繪標題列、真正的打亂

- 狀態：已採納
- 日期：2026-10-24
- 影響範圍：`app/lib/ui/` 的外殼、導覽、主題、播放頁、播放列、佇列、歷史、搜尋、首頁、電台、音樂庫、匯入進度、設定；`app/lib/platform/` 的字型與標題列；`app/lib/playback/queue_model.dart`；資料表 `appearance_settings`、`layout_state` 的欄位與新表 `search_history`；插件宿主 API 的選填欄位 `viewCount`、`webUrl`；`app/lib/legacy_import/` 的設定轉換

## 背景

擁有者試用 M5 的 dev 版後認為新版 UI 不如舊版（例：匯入 1195 首的歌單看不到進度），2026-10-24 決定在 M6 前插入里程碑 U：**以舊版 UI 為底，再在上面優化**。

依據：

- 逐項對照 94 項（`.trellis/tasks/archive/2026-10/10-24-ui-legacy-parity/research/compare-*.md`，B-01–B-34、L-01–L-34、P-01–P-26）。
- 設計稿：8 個畫面 × iPhone／Windows／Mac，22 組 A／B 選擇點（原始檔 `research/design/`）。
- 擁有者看過設計稿後決定「全都按推薦」：有選擇點的照設計稿的推薦，其餘照對照文件的建議；另有 4 項明確選「照舊版」（B-19、B-33、L-27、P-06）。

這推翻了以下決定（各段加上指向本 ADR 的補充）：

- ADR 0024 §決定 1：播放頁局部毛玻璃（拿掉）。
- ADR 0024 §決定 3：導覽元件（改成舊版可展開側欄）。
- ADR 0024 §決定 4：播放頁方案 B（改成舊版左封面右歌詞）。
- ADR 0024 §決定 5：播放列位置與進度條（改成橫跨整個視窗、頂端細線；三段控制保留）。
- ADR 0024 §決定 8：Ctrl+L／Ctrl+Q 的語意、Apple 平台的修飾鍵。
- ADR 0033 §決定 5：導覽五項（加入「佇列」成六項）。
- ADR 0018 §決定 5：另加真正的打亂。位置式隨機不變。

## 考慮過的選項

### 範圍

- **只對齊外觀，保留 ADR 0024 選過的不同之處**：擁有者明說要以舊版為底。否決。
- **整套搬回舊版，不保留新版的改進**：會丟掉無障礙、快捷鍵、焦點區、list-detail 設定、插件化帶來的選單項目。否決。
- **以舊版為底，逐項保留新版的改進**：採用（每項的結論在任務的 `prd.md`）。

### 佇列入口

- **播放列加佇列鈕，開右側面板或底部面板**：不必推翻 ADR 0033，但佇列仍然低一層。否決。
- **佇列回到導覽，成為第六項**：兩字標籤放六項不擠；佇列是長歌單連播的核心畫面。採用。Material 3 建議導覽列放三到五項，這是有意偏離，理由是舊版就這樣而且擁有者選了它。

### 液態玻璃（2026-10 重查）

- **Apple 平台用液態玻璃**：Flutter 官方元件還沒釋出（#170310），Cupertino 正拆成獨立套件；兩套外觀要維護兩倍；ADR 0024 的否決理由仍成立。否決。
- **全平台同一套舊版風格的 Material，加上 Apple 平台慣例**：採用。

### Windows 與 Mac 的標題列

- **系統標題列**：深色主題下多一條系統灰條，和舊版不同。否決。
- **自繪標題列**：舊版 Windows 就是這樣（`window_manager`，`TitleBarStyle.hidden`）。採用；Mac 用同高同色的自繪列，紅綠燈留在左側（系統按鈕，不重畫）。

### 打亂

- **不放打亂鈕**：擁有者選了要真正的打亂。否決。
- **打亂鈕＝隨機開關**：外觀像舊版但語意不同，兩處都叫「隨機」容易混淆。否決。
- **真正的打亂（舊版 `QueueManager.shuffle`）**：採用。

## 決定

1. **基準**：UI 以舊版為底。每個畫面照設計稿與任務 `prd.md` 的 R1–R7；新版的無障礙、快捷鍵、焦點三區、巢狀導覽、選單項目、狀態標示保留。
2. **導覽**：首頁｜搜尋｜音樂庫｜佇列｜電台｜設定，各寬度同一組；手機的佇列是整頁。App 開在首頁。
   - compact 用底部導覽列；medium 以上用舊版的側欄：收合 72dp、展開 256dp 並顯示 FMP 名稱，展開狀態依裝置記住（舊版 `railExpanded`）。取代 `NavigationRail` 與常駐 `NavigationDrawer`。
   - 頁頂用舊版的置中 AppBar；多選時換成選取列（ADR 0033 §決定 10 的行為不變）。
   - 右側「正在播放」面板仍在 expanded 以上，但沒有曲目時不顯示；內容補「下一首」、點封面或標題開原網頁、加入歌單。
     - 修訂（2026-10-27，U 驗收）：內容區至少留 360dp（M3 固定窗格寬）。側欄展開加面板放不下時，側欄畫成收合，記住的展開狀態不變；這時按展開會一併收起面板。舊版在 840dp 以上照擠。
3. **播放頁**：
   - expanded 以上照舊版：左 5 份放封面（上限 420dp，大圓角加陰影）與控制，右 7 份放歌詞；沒有歌詞時單欄置中（內容寬上限 720dp）。M7 之前一律單欄。
   - 控制區照舊版：曲名置中粗體、80dp 實心播放鍵，沒有毛玻璃底板。
   - 頂列：收合、加入歌單、輸出裝置與音量（桌面）、資訊（開曲目詳細）、「⋯」。曲目詳細在窄版是底部面板，寬版是側邊面板，內容沿用 `TrackDetails`。
   - 從底部上滑開啟、下滑關閉；Esc、返回鍵、佇列清空時自動關閉照舊。
   - 橫向手機（寬大於高且高小於 520dp）用舊版的左右矮版面。
   - 取消方案 B 的右欄分頁與 extraLarge 三欄。
4. **播放列**：橫跨整個視窗（含側欄下方），頂端 2dp 進度細線，滑鼠移入或拖曳時變 6dp、顯示把手與時間；三段控制與「點擊區和按鈕分開」照 ADR 0024 §決定 5。
5. **主題與外觀**：
   - 預設種子色 `#6750A4`，加上舊版的 8 個 preset（`lib/ui/theme/theme_preset_colors.dart`）與自訂色；元件主題（卡片、輸入框、清單列、AppBar、導覽指示）照舊版。
   - 字型：每個平台一份固定清單，加「系統預設」。這是舊版 `AppTheme.availableFonts` 的做法，清單內容改成繁中為主，由平台層提供。CJK fallback 照 ADR 0024 §決定 2，Apple 平台繁中用蘋方（`PingFang TC`）。
   - `appearance_settings` 加 `seed_color`、`font_family`（可空，空＝預設）；側欄展開狀態依裝置記住，放 `layout_state.rail_expanded`（與面板寬度同表）；拿掉播放頁分頁後 `layout_state.player_tab` 刪除。
6. **標題列**：Windows 用自繪標題列（36dp、主題色、App 名稱加最小化、最大化、關閉），經平台層的能力宣告。套件是 `window_manager`，版本在實作時照 ADR 0021 §後果的維護狀態再查。Mac 的自繪列由 macOS 平台任務實作，規格同設計稿。
   - 更正（2026-10-27，U PR 15）：查過 pub.dev，`window_manager` 0.5.2（2026-07-04 發版）是最新的穩定版，沒有停止維護的標示（ADR 0021 §後果已更正過同一件事），採用 `^0.5.2`。
7. **快捷鍵**：ADR 0024 §決定 8 的表照舊，有三處改動：
   - Apple 平台的 Ctrl 一律換成 ⌘。
   - 開佇列在 Windows 是 Ctrl+Q，Mac 是 ⌥⌘U（Apple Music 的「顯示佇列」），避開 ⌘Q。現在都是切到「佇列」目的地。
   - Ctrl+L／⌘L 在 M7 之前不做事。
   - 修飾鍵由平台層提供，`lib/platform/` 以外不判斷平台（`fmp_platform_checks`）。
8. **打亂**（ADR 0018 §決定 5 的補充）：佇列頁頂部的「打亂」把整個佇列重排一次（不可復原），目前這首移到第一位；Mix 模式時停用。隨機開著時按打亂，重排後重新產生一輪位置式隨機，目前這首開頭；位置式隨機的語意不變。
9. **搜尋**：
   - 搜尋歷史存在新表 `search_history`（關鍵字、最後搜尋時間）。備份照 ADR 0034 歸「帶走」；舊版的搜尋歷史由舊資料匯入一併轉入。
   - 「全部音源」由宿主依序向每個已啟用、有 `search` 能力的插件發出同一個搜尋，結果依插件順序分組顯示。單一插件失敗只在它那一組標示，分頁游標各插件分開。
   - 捲到底自動載入下一頁。
10. **播放數與原網頁**：宿主 API v1 加兩個選填欄位，`hostApiVersion` 維持 1（ADR 0028 §決定 1、ADR 0032 的前例）：曲目的 `viewCount`（整數，曲目列與排行有值才顯示）、`TrackDetail.webUrl`（右側面板與曲目詳細點封面或標題時開啟，要過 manifest 的允許主機檢查，沒有就不可點）。VIP 標記不做。
    - 補充（U PR 16，擁有者 2026-10-27 核可）：`LiveRoom` 另加選填的 `area`（分區的短文字，宿主去掉前後空白、空的當沒有），搜尋結果的直播間列有值時顯示（B-27）；電台列要把它存進資料庫才有，不在 U。
11. **匯入進度**：
    - 網址匯入與帳號匯入顯示「已匯入 n／M 首」：M 取插件給的總數，帳號清單已有首數時用它；兩者都沒有時顯示「已讀 n 首」。
    - 兩者都可以取消：新匯入的歌單取消就整張放棄（含已寫入的頁，連同項目與孤兒曲目一併刪除，什麼都不留）；重新匯入或刷新既有的歌單只是停下，這次已寫入的頁保留，歌單照 ADR 0033 §決定 2 的「不完整」處理。帳號匯入取消時，已經做完的歌單留著，取消當下正在匯入的那張放棄。（2026-10-25 擁有者決定：取消就是放棄）
    - 帳號匯入改成全頁，列出每張歌單的進度。
12. **舊資料匯入**：`primaryColor`、`fontFamily`、`railExpanded`、搜尋歷史這四項從「未匯入的設定」改成會匯入。舊字型不在新清單時退回系統預設。已經匯入過的資料不補匯：只有 dev 試用者匯入過，可以用設定頁「從舊版匯入…」重做。
13. **Apple 平台慣例**：iPhone 的安全區域，iOS 頁面右滑返回（`CupertinoPageTransitionsBuilder`）；Mac 的紅綠燈標題列。Dart 側的設定隨 U 實作；原生部分與實機驗證交給 macOS／iOS 平台任務，因為 App 目前在 Apple 平台還不啟動。

採用的慣例：舊版 FMP 的版面與主題（`lib/ui/` 凍結的程式碼，各項出處在對照文件）；Apple Music 的 Mac 快捷鍵（support.apple.com 的 Keyboard shortcuts in Music on Mac）；Material 3 的元件。

## 後果

- 好的：擁有者熟悉的外觀與動線回來了；佇列一鍵就到；大歌單匯入看得到進度、也能取消；主題色與字型回來了；新版的無障礙與鍵盤操作保留。
- 壞的：
  - 導覽六項超過 Material 建議的五項。
  - 寬版播放頁在 M7 之前只有單欄，看不到佇列（佇列改走導覽）。
  - 自繪標題列要自己處理拖曳、最大化與焦點，`window_manager` 有維護風險。
  - 宿主 API 加欄位，插件與 FMP 要同一輪改。
  - 「全部音源」一次搜尋會對每個音源各發一個請求。
- 之後要注意：
  - M7 的歌詞放進右 7 份，窄版的封面／歌詞切換也在 M7 回來。
  - macOS 平台任務照第 6 條做 Mac 標題列。
  - `window_manager` 的維護狀態。

## 如何確認

- widget 測試：
  - 六個導覽項在三種寬度、App 開在首頁；側欄展開狀態記住。
  - 播放頁 expanded 與 compact 的版面、沒有曲目時面板不顯示、播放列細線的 hover 與拖曳。
  - 佇列頂部的橫幅、跳頂／底、打亂與清空；歷史的篩選、搜尋、排序與兩種刪除。
  - 搜尋歷史的寫入與清除、自動載入；匯入的 n／M 與取消。
  - 外觀設定的 preset、自訂色、字型。
  - 快捷鍵：以平台層的假實作測 Ctrl 與 ⌘ 兩組，以及 ⌥⌘U。
- guideline：上述新畫面在淺色與深色下過 `labeledTapTargetGuideline` 與 `textContrastGuideline`（ADR 0024 §如何確認的同一套）。
- golden：播放頁、播放列、面板的 golden 換成新版面（只守結構）。
- 資料庫：`appearance_settings`、`layout_state` 的欄位與 `search_history` 的 migration 三種測試、schema 快照；ADR 0034 的表歸類測試把 `search_history` 列進「帶走」。
- 佇列：`QueueModel` 的打亂測試（目前這首在第一位、Mix 時擋下、隨機開著時重新產生一輪）。
- 插件：`viewCount`、`webUrl` 的 DTO 解析測試（含不允許的主機）與契約 fixture；三個官方插件有值時填入。
- 舊資料匯入：四項設定的轉換測試（含不在清單的字型）。
- 實機（ADR 0027）：每個 PR 在 Android 驗；動到桌面互動或標題列的在 Windows 驗；里程碑驗收兩平台走完整流程，並以 1000 首以上的歌單驗匯入進度與取消。
