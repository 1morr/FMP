# 0020 — 下載與權限：background_downloader、每首一份依音源存放、可寫標籤的格式、只標記不刪除的對帳、統一權限入口

- 狀態：已採納
- 日期：2026-09-28
- 影響範圍：下載模組、`downloads` 表、下載根目錄與檔名、內嵌標籤與 sidecar、啟動對帳、平台層 `PermissionGateway`、下載相關設定

## 背景

舊專案（`.trellis/tasks/archive/2026-09/09-28-design-downloads/research/current-state.md`、`docs/audit/downloads.md`，已以程式碼核對）：

- 每任務一個 isolate、原生 `HttpClient`、事件加 5 秒輪詢；只在 App 行程內下載（N8）。
- 續傳只送 `Range`、不驗證（N4）；沒有自動重試；每次啟動清掉失敗任務（N7）。
- 下載與播放共用音質（N5）；副檔名一律 `.m4a`、沒有內嵌標籤（N6、B13）。
- 依歌單分資料夾，同一首歌在兩張歌單下載兩份；歌單改名不改資料夾（N3）。
- 啟動掃描以「資料夾名＝歌單名」重建關聯、掃不到就清路徑（N1 的資料遺失路徑）；播放時找不到檔案就永久清掉路徑（N9）。
- Android 改下載路徑的 UI 被隱藏（N2）；沒有宣告 `POST_NOTIFICATIONS`；權限走自有 MethodChannel（N10、N11）。

舊 ADR 0004（Android 以 `MANAGE_EXTERNAL_STORAGE`＋路徑、不用 MediaStore）描述舊專案；本 ADR 在 `app/` 延續其儲存做法。

## 考慮過的選項

- **自寫 isolate 下載器（舊版）**：否決。續傳驗證、背景下載、重試、通知都要自寫。
- **`flutter_downloader`**：否決，不支援桌面。
- **SAF URI 下載**：否決。免權限，但 `background_downloader` 對 URI 目標不能暫停續傳；FMP 不上架商店，可用 `MANAGE_EXTERNAL_STORAGE`。
- **依歌單分資料夾（舊版）**：否決。同一首歌多份、歌單改名要搬檔、移出歌單時檔案去留難定。
- **依歌手分資料夾**：否決（擁有者指出）。B 站、YouTube 的「歌手」其實是上傳者。
- **下載最高音質含 Opus／WebM**：否決（擁有者 2026-09-28 選擇）。WebM 幾乎沒有可靠的標籤寫入方案，只有小眾套件或已退役、GPL 的 FFmpeg 分支。
- **以資料夾名重建關聯、掃不到就清路徑、找不到檔就永久清路徑**：否決，N1、N9 的來源。
- **跨網址接續續傳**：否決。網址過期就重解析、從頭下載；音檔多為數 MB。

## 決定

1. **引擎**：`background_downloader`。
   - Android 在背景繼續下載（WorkManager，Android 14+ 使用者發起工作並顯示通知）。
   - 桌面只在 App 執行中下載：最小化或縮到托盤照常，關閉即暫停，下次啟動自動續傳。
   - 請求帶插件候選串流的標頭、不帶帳號憑證（ADR 0012）。這是網路層之外唯一的 HTTP 出口：下載網址寫 log 前經 ADR 0011 的遮蔽函式，測試以假的下載器介面注入。
   - 同時下載數 1–5（預設 3）、同一主機最多 2；事件驅動，不輪詢。
2. **流程**：建立紀錄 → 經插件 `resolveStream`（用途＝下載、不走記憶體網址快取）→ 下載到 App 私有暫存 → 寫內嵌標籤與 sidecar → 搬到最終位置 → 完成。
   最終資料夾不會出現半成品。
3. **續傳與失敗**：
   - 續傳以強 ETag 驗證，不符或不支援就從頭下載；網址過期或 403 時重解析一次、從頭下載；
   - 網路錯誤以指數退避重試 2 次；
   - 失敗與暫停任務跨重啟保留，直到使用者重試或清除。
4. **組織與命名**：每首歌只存一份，依音源（插件 id）分資料夾。
   - 單曲：`{根目錄}/{音源}/{標題} [{影片 id}].{副檔名}`；
   - 多分 P：`{根目錄}/{音源}/{影片標題} [{影片 id}]/P01 {分P標題}.{副檔名}`。
   
   標題截到 80 字以符合 Windows 路徑上限。紀錄存絕對路徑；「已下載」頁的歌單分類由資料庫關聯算出。
5. **根目錄**：
   - 預設 Android `Music/FMP`、Windows `%USERPROFILE%\Music\FMP`、Linux XDG 音樂目錄下 `FMP`；舊資料匯入沿用舊下載目錄。
   - Android 可在設定頁更改並重新授權；更改時選「搬移現有下載」或「只改之後的位置」。
   - Android 以 `MANAGE_EXTERNAL_STORAGE`＋路徑寫入。
6. **格式與標籤**：下載只接受 m4a（AAC）、flac、mp3，YouTube 下載取 AAC；播放不受影響。
   - 副檔名照實際格式；
   - 內嵌標題、歌手（音源回報的值）、專輯（多分 P 用影片標題）、封面、來源網址（候選 `audio_metadata_reader`）；
   - sidecar 保留：同檔名 `.json`（曲目鍵、音源、影片 id、分 P、標題、時長、下載時間）、`.jpg` 封面，選項開啟時另存 `.avatar.jpg`。
7. **與音樂庫的關聯**：`downloads` 表以曲目鍵關聯（ADR 0019 的孤兒判定納入它）。刷新移出歌單不刪下載；下載只由使用者在下載頁刪除（檔案、sidecar、紀錄）。
8. **啟動對帳**（登記在啟動維護清單，ADR 0017）：
   - 檔案不在就標「檔案遺失」、不刪紀錄，播放改走線上，並提供重新下載或移除紀錄；
   - 根目錄不可用就標「儲存位置無法使用」、不動紀錄；
   - 有 sidecar 或檔名帶影片 id 但沒紀錄的檔案，自動建立紀錄並認回曲目；
   - 對帳永遠不自動刪檔或刪紀錄。
   
   舊下載檔留在原位，匯入時依舊 sidecar 建立紀錄。
9. **權限統一入口**：平台層 `PermissionGateway` 依能力宣告需要的權限：
   - 下載資料夾寫入（Android `MANAGE_EXTERNAL_STORAGE`）；
   - 下載通知（Android 13+ `POST_NOTIFICATIONS`，第一次下載時請求）；
   - 安裝更新（`REQUEST_INSTALL_PACKAGES`）；
   - 顯示在其他應用上層（Android 懸浮歌詞，ADR 0021）。
   
   流程固定為說明 → 請求 → 被拒時說明影響並提供「前往系統設定」→ 回到 App 時重新檢查，永久拒絕另外處理。
   通知被拒照樣下載；儲存被拒不開始下載並引導設定。Android 用 `permission_handler`（見「如何確認」的 Windows 實測）。
10. **設定**：下載音質（高／中／低，預設高）與播放分開；同時下載數、下載圖片選項、根目錄沿用。

採用的慣例：Finamp、Namida、NewPipe 的「資料庫記錄＋啟動對帳」；NewPipe 的下載前景通知與權限說明；RFC 9110 的 `If-Range`／強 ETag 續傳語意；
`background_downloader` 官方的暫存與背景模型。

## 後果

- 好的：
  - 同一首歌不重複佔空間；歌單改名、刷新移除都不影響檔案；
  - 對帳不再遺失資料；
  - 所有下載檔都有正確副檔名與標籤；
  - Android 背景可下載；
  - 權限流程一致。
- 壞的：
  - Windows 關掉 App 就不下載；
  - YouTube 下載不是最高位元率；
  - 在 App 外面看，資料夾不依歌單分組；
  - 下載是網路層之外的一個 HTTP 出口，要靠遮蔽與測試介面守住。
- 之後要注意：iOS／macOS 的下載位置與「檔案」App 可見性由該平台任務定；已下載內容的容量管理在功能凍結待辦。

## 如何確認

- 單元測試（假下載器）：
  - 並行上限；失敗任務跨重啟保留；
  - 網址過期時重解析並從頭下載；ETag 不符從頭下載；
  - 格式過濾；暫存 → 標籤 → 搬移任一步失敗時最終資料夾沒有半成品。
- 對帳測試：
  - 檔案遺失不刪紀錄；根目錄不可用不動紀錄；
  - 無紀錄的檔案依 sidecar 或檔名認回；
  - 從不刪檔。
- 路徑測試：檔名清理、Windows 路徑長度、保留名。
- 權限流程測試（假的 `PermissionGateway`）：拒絕、永久拒絕、從設定回來重新檢查。
- 依賴方向（`fmp_layer_imports`，ADR 0015）：`background_downloader` 只在下載模組、`permission_handler` 只在平台層。
- 加入下載的里程碑實測：
  - `permission_handler` 在 Windows 是否使 FMP 出現在位置權限清單，會就改為 Android 專用的自有 MethodChannel；
  - 寫入的標籤能被常見播放器讀到；
  - Android 以 `MANAGE_EXTERNAL_STORAGE` 搬移到使用者資料夾可行。
