# 0038 — 音源以隨 App 打包的 JS 插件實作

- 狀態：已採納
- 日期：2026-11-06
- 影響範圍：`app/lib/plugins/`、`app/plugins/`、宿主 API、發版內容

## 背景

舊版的音源特定分支散在 29 個檔、73 處，新增一個音源最少要改 15 個檔。新版要讓 App 只當載體：搜尋、串流、帳號、會員狀態、遠端歌單讀寫、歌詞都由音源提供，介面依插件宣告的插件能力出現入口。上一輪重寫（tag `archive/trellis-rewrite-20261106`，ADR 0014、0030）已經用 JS 插件跑通四個平台，但插件放在另一個 repo，首次啟動要先安裝，宿主 API 也沒有 VIP 與存取等級。

## 考慮過的選項

### 選項 A：JS 插件，另一個 repo，App 不內建（上一輪）

修音源不用發 App。缺點是要維護兩個 repo，契約測試要釘住對方的 commit；CDN 快取會讓 SHA 暫時對不上；首次啟動要先裝插件。

### 選項 B：Dart 模組，編譯進 App

除錯最容易，只有一種語言。缺點是修音源就要發 App，YouTube 這種每幾個月就變的音源修復會慢；也用不了 YouTube.js 這類 JS 生態的解析庫。

### 選項 C：JS 插件，原始碼在本 repo，隨 App 打包，可單獨更新

保留免發 App 修復的好處；宿主 API 和插件在同一個 commit 一起改，契約測試直接在本 repo 跑；首次啟動不用安裝。

## 決定

選 C。插件用 TypeScript 寫，以 esbuild 打包成單一 JS 檔（產物提交進 repo，`tool/check.dart` 檢查它是否最新），隨 App 打包；更新從 GitHub Release 的 `index.json` 取得，安裝前驗 SHA-256，並經使用者確認。插件只能連 manifest 宣告的網域，沒有檔案系統與 socket。第一版不支援第三方插件來源。

能力宣告參考 Spotube v6：功能與權限分開，有遠端歌單寫入。方法可選的做法參考 MusicFree。不上 App Store，所以不受 Guideline 2.5.2 限制（brief〈查證過的事實〉R6）。

## 後果

- 好的：音源修復不用發 App；宿主不含任何音源專屬的邏輯；新增音源等於新增一個插件目錄。
- 壞的：JS 除錯比較難；四個平台都要打包 JS 引擎；開發插件的機器要裝 Node；宿主 API 發佈後要維持相容。
- 之後要注意：宿主 API 在第一版發佈（`app-v2.0.0`）時凍結，之後只能加選填欄位。JS 引擎由 M0 的實驗決定，結論寫回 brief。

## 如何確認

- 依賴規則測試：Dart 端不得出現音源識別碼的字面值分支，音源邏輯只能在 `app/plugins/`。
- 每個插件套同一套契約測試（fixture 重播）。
- `tool/check.dart` 檢查打包產物與原始碼一致。

三者由 M0 建立；建好之前這份 ADR 沒有閘門。
