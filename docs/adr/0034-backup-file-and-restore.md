# 0034 — 備份檔是去掉裝置與帳號資料的資料庫副本，還原是取代並重啟、保留目前的登入

- 狀態：已採納
- 日期：2026-10-15
- 影響範圍：`app/lib/data/database/database_backups.dart`、`app/lib/app/`（備份、還原與重啟的流程）、設定頁的「備份與還原」區、Debug 頁的「從備份還原」、對外的持久化格式（備份檔）

## 背景

「備份」在文件裡有四種說法（`.trellis/tasks/archive/2026-10/10-15-m4-library-sync/research/m4-scope-digest.md` 矛盾 1）：

- ADR 0025 §決定 9 的更正（M3）：重設資料前以 `VACUUM INTO` 把資料庫複製到 `backups/fmp-<時間>.db`，「從備份還原」換回該檔並重啟，「M4 的 E16 匯出格式另定」。M3 的還原先清掉憑證與登入 WebView，還原後一律重新登入。
- `milestones.md` 的「新格式的備份與還原」（E16，擁有者勾保留）；ADR 0010 的影響範圍列了「備份格式」，決定裡沒有定義。
- ADR 0011 §決定 7「設定包含在備份中」；M2 定了 `layout_state` 不進備份；ADR 0021 定了 AI key 不進備份。
- ADR 0015 §決定 8：開發版的真實資料以「還原正式版備份」帶入。

舊版是單一 JSON 檔（`fmp_backup_<時間>.json`，`kBackupVersion = 5`），每一類資料各寫序列化與合併規則，匯入時可勾類別、同名歌單略過；那份格式的匯入屬 M5（ADR 0010 §決定 4）。

擁有者 2026-10-15 決定：資料庫副本＋保留登入——`VACUUM INTO`，排除 `layout_state`、`accounts`、`plugin_storage`、`scheduler_runs`；含已安裝的插件，還原時以確認框列出插件與網域代替安裝確認；還原＝取代並重啟、還原前自動備份；保留目前的登入；不含憑證、Cookie、AI key；入口在設定頁「備份與還原」區。

## 考慮過的選項

- **版本化 JSON＋合併匯入、可勾類別（舊版）**：最像舊版，但每張表都要寫序列化與合併規則，並跟著每一版 schema 改；合併的規則（同名、同遠端 id、重複曲目）還要另外定。否決。
- **資料庫副本＋合併匯入**：合併規則同樣要定，只省了序列化。否決。
- **資料庫副本，取代並重啟**：FMP 的設定本來就在資料庫裡，副本就是完整的備份；`user_version` 就是格式版本，比目前舊的檔照常 migration；M3 已實作大半（`DatabaseBackups`、`DataReset`）。代價是沒有合併。採用（NewPipe 的「匯出資料庫」、AntennaPod 的「匯出／匯入資料庫」）。
- **還原後登出全部（M3 現況）**：最省事，但換裝置或還原舊備份後每個音源都要重新登入。否決（擁有者決定保留）。
- **zip 包資料庫與設定檔**：FMP 沒有資料庫以外的設定。否決。

## 決定

1. **備份檔**＝單一 SQLite 檔 `fmp-backup-<UTC 時間>.db`。做法：`VACUUM INTO` 到資料目錄的暫存檔 → 在暫存檔上清掉不帶走的資料 → `VACUUM`（刪掉的列不留在空閒頁）→ 以 `FileDialogs.saveFile` 交給使用者存 → 刪暫存檔。
2. **不帶走的資料**：
   - 整張表：`layout_state`（裝置的版面）、`accounts`（帳號顯示資訊）、`plugin_storage`（插件的匿名 cookie 等裝置身分）、`scheduler_runs`（排程的上次成功時間）；
   - 只屬於這台的欄位：`playback_settings` 的輸出裝置兩欄、`developer_settings.plugin_dev_folder`，以及 `installed_plugins` 裡插件開發工具補的標記列（`from_dev_folder`）。
   - 一律不在資料庫、所以本來就不含：憑證與 Cookie（secure storage，ADR 0012）、AI key（ADR 0021）、快取（`cache.db`，ADR 0016）、log、已下載的音檔。
   - 其餘全部帶走：設定各組、每音源設定、歌單與項目、曲目、播放歷史、佇列與播放狀態、電台、匹配結果、榜單設定、自訂 index、已安裝的插件（含腳本與檢查案例）。
3. **版本**：備份檔的 `user_version` 就是 schema 版本。比目前的新就拒絕（「這份備份來自較新版的 FMP」）；`user_version` 為 0 或缺必要的表就拒絕（「這不是 FMP 的備份」）；比目前的舊就照常 migration（ADR 0010 §決定 3）。不另加 manifest。
4. **還原**（設定頁的「從備份檔還原」與 Debug 頁的「從備份還原」同一條路徑）：
   1. 把選的檔複製到資料目錄的暫存檔，檢查 SQLite 標頭、`user_version`、`PRAGMA integrity_check`，以 App 的 migration 開啟到目前版本——任何一步失敗就拒絕，什麼都不動；
   2. 確認框列出備份裡的插件（名稱、版本、會連的網域）與 ADR 0030 §決定 8 的警告，並說明「目前的資料會被取代；取代前會自動備份」——**這一步代替安裝確認**（還原不經過安裝流程）；
   3. 自動備份目前的資料庫（`DatabaseBackups.create`，失敗就停）；
   4. 把目前的 `accounts` 列與第 2 條「只屬於這台」的值寫進暫存檔，取代暫存檔裡的；
   5. 關閉資料庫、以暫存檔取代 `fmp.db`（原檔改名留著），重啟（ADR 0025 §決定 9 的重啟做法）。
   - 憑證與登入 WebView 都不動：目前的登入在還原後照舊有效。
   - 開發版可以還原正式版的備份（ADR 0015 §決定 8），反方向不擋。
   - 補充（2026-10-22，M4 PR 22）：備份檔是外來檔案，第 1 步另加四道防護：
     - 有 trigger 或 view 的檔在 migration 前就拒絕；所有連線都設 `trusted_schema = OFF`。
     - migration 後以 App 建的全新 schema 逐表複製資料，再跑 `foreign_key_check`：改過欄位定義、CHECK 或型別的表不會留下來。
     - 確認框的插件名稱、版本與網域取自腳本標頭的 manifest（執行時用的那份）；列的欄位與標頭不一致就拒絕。這台也裝了同 id 時，標出「比這台的舊」與多出的網域；會帶入的自訂 index 也列出來。
     - 腳本解析不出來（壞了，或這個版本不支援）的插件從還原中刪掉，連同它的每音源設定與榜單設定，並在確認框列出；整份備份照常還原。
     - 第 4 步對第 2 條的表一律以清單為準：`accounts`、`layout_state` 帶這台的，`plugin_storage`、`scheduler_runs` 清空。
   - 補充（2026-10-22，M4 備份後續）：每音源設定 `source_settings.browse_as_logged_in`（「以登入身分瀏覽與播放」）跟著這台的登入，也屬於「只屬於這台」，但該表每個插件一列，所以另有以鍵對應的清單（`backupDeviceKeyedColumns`，鍵是 `plugin_id`，閘門檢查它是主鍵或 unique）：匯出設成空值；第 4 步先把備份裡每一列的這一欄清成空值，再對暫存檔裡已安裝（`installed_plugins`）的插件，把這台非空的值寫進同 `plugin_id` 的列（沒有那一列就新增，其餘欄位為空值；暫存檔沒裝的插件，這台的值丟掉）。這台沒有那一列就維持空值（預設）。同一列的 `match_target`、`match_rank` 照備份。不改備份檔格式版本，舊檔照樣能還原。還原前自動備份的檔案，若在還原之後、該插件的列已經不在時才拿來還原，這一欄回到預設。
5. **入口**：設定頁新的「備份與還原」區（「匯出備份」「從備份檔還原」）。Debug 頁保留重設資料前的自動備份與「從備份還原」。不做自動定期備份（舊版沒有）。

採用的慣例：NewPipe 的「匯出資料庫」（匯入取代並重啟）、AntennaPod 的「匯出／匯入資料庫」；SQLite 官方以 `VACUUM INTO` 做線上備份；舊版匯入時保留這台的輸出裝置與下載資料夾（`backup_service.dart`）——裝置專屬的值不跟著備份走。

## 後果

- 好的：備份涵蓋資料庫裡的一切，不必替每張新表寫序列化；換裝置後插件、設定、歌單、匹配結果都在，登入照舊；舊版本的備份靠既有的 migration 就能還原；備份檔不含任何憑證或 cookie。
- 壞的：沒有合併——匯入別台的備份會取代這台的歌單與歷史（確認框寫明，並先自動備份）；備份帶著插件腳本，還原時的確認框是唯一的一道檢查；備份檔是 SQLite 格式，使用者不能用文字編輯器看。
- 之後要注意：
  - M5：舊 JSON 備份由 `legacy_import` 轉換（ADR 0010 §決定 4），是否共用「從備份檔還原」的入口由 M5 定；
  - M6：下載紀錄會跟著備份走，但檔案路徑只對原本那台有效，換裝置後的處理由 M6 定；
  - M7：歌詞匹配結果在資料庫，自動帶走；AI key 在插件憑證區，不帶走；
  - 新增的表若是裝置專屬或帶秘密，加表的 PR 要把它加進第 2 條的清單與測試。

## 如何確認

- 備份測試（真的檔案資料庫）：匯出的檔裡第 2 條的表為空、欄位為空、標記列不在；在 `plugin_storage` 寫一個假 cookie 值後匯出，檔案的位元組裡找不到它（`VACUUM` 之後不留在空閒頁）；匯出的檔可以開啟且其他表的筆數相同。
- 還原測試：較新版、`user_version` 為 0、損壞的檔被拒絕且資料庫不變；較舊版的檔 migration 後開得起來；還原後 `accounts` 是還原前這台的列、`CredentialStore` 沒有被清、輸出裝置與開發資料夾是這台的值；自動備份失敗時不取代；確認框列出備份裡的插件與網域。
- 新表的守門：一個測試列出主資料庫的所有表，每張表必須在「帶走」或「不帶走」其中一份清單裡，新加的表沒有歸類就紅（雙向變異：漏一張紅、改清單順序不紅）。
- 實機（ADR 0027）：Windows 匯出、Android 還原（與反方向各一次），登入保留、插件確認框正確、自動備份存在（M4b 驗收）。
