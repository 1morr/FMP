# 0019 — 音樂庫與同步：外鍵關聯、遠端權威的單向刷新、明確的遠端操作、共用匹配核心

- 狀態：已採納
- 日期：2026-09-28
- 影響範圍：`playlists`／`playlist_remote`／`playlist_entries`／`tracks`／`track_origins`／`match_results` 表、匯入與刷新流程、
  遠端歌單操作、僅元資料來源的匯入預覽、共用匹配評分核心、孤兒曲目清理

## 背景

舊專案（`.trellis/tasks/archive/2026-09/09-28-design-library-sync/research/current-state.md`，已以程式碼核對）：

- 本地與匯入歌單同一個 collection，只靠 `sourceUrl != null` 區分（`playlist.dart:70`）；曲目與歌單的關係是手動維護的整數陣列加反向 `playlistInfo`，
  沒有外鍵，曾因此遺失資料（ADR 0010）。
- 刷新只在遠端資料完整時才刪除，否則靜默「只增不刪」且 UI 不顯示（`playlist_mutation_repository.dart:531-532,841-873`）；
  遠端改標題不會同步；重新匯入會覆寫「使用登入刷新」與間隔（M12）。
- 遠端歌單被刪或變私人沒有狀態，只有一次被壓成「發生錯誤」的 toast，排程繼續重試。
- Spotify／QQ 匯入與歌詞匹配是兩套評分；匯入的手動重搜只依播放量排序。

擁有者已定（`docs/audit/questions.md` B1／B2 備註）：遠端是權威、只往下同步；匯入歌單不能在本地增刪曲目；
保留明確標示的遠端操作；名稱、描述、封面、自動刷新設定可在本地改。

## 考慮過的選項

- **本地與匯入同表、只靠網址區分；手動維護反向關係**：否決，資料遺失的來源。
- **遠端已無的曲目保留並標「遠端已移除」**：否決（擁有者 2026-09-28 選擇跟遠端一致移除），會累積「刪了還在」的曲目。
- **部分失敗時靜默只增不刪**：否決，改為顯示「部分完成」。
- **「加入遠端歌單」也加確認框**：否決；勾選目標歌單已是明確操作（Namida：加入不確認、移除才確認）。
- **每張歌單各存「使用登入刷新」**：否決，改依 ADR 0012 的音源設定。
- **匯入與歌詞兩套評分、手動重搜只看播放量**：否決（ADR 0014 決定 9）。
- **`fuzzywuzzy`**：否決，GPL-2.0。
- **單向同步用 LCS／Myers 差異**：不需要；以曲目鍵集合差集加遠端順序即可（Finamp 的慣例）。

## 決定

1. **資料模型**：
   - `playlists`（`kind`：`local`／`imported`／`mix`，名稱不唯一）；
   - `playlist_remote`（插件、遠端 id、擁有者、名稱／描述／封面的本地覆寫旗標、上次刷新時間與結果、狀態）；
   - `playlist_entries`（歌單 FK 連帶刪除、位置、曲目鍵 FK、遠端項目 id）——**不對（歌單, 曲目鍵）設唯一**，因為 YouTube 歌單可含重複影片；
   - `tracks`（ADR 0005 的曲目鍵格式照搬）；
   - `track_origins`（原始平台與 id）；
   - `match_results`（選定曲目、分數、使用者改選）。
   
   開啟資料庫時 `PRAGMA foreign_keys = ON`。孤兒曲目以查詢判斷（沒有被歌單項目、佇列、下載紀錄參照），登記在啟動維護清單（ADR 0017）。
   更正（2026-10-01，M2 規劃）：`tracks` 在 M2 先建（只有表與 repository，佇列與播放歷史以外鍵參照，欄位見 M2 的 `design.md` §3.1），M4 只加欄位與其他表；孤兒的參照者另含播放歷史。
2. **刷新**（經插件 `importPlaylist`，排程見 ADR 0017，登入依 ADR 0012）：
   - 以曲目鍵比對，遠端有本地無則新增，本地有遠端無則**從該歌單移除**（下載檔不刪），順序完全照遠端；
   - 曲目元資料與可用狀態照遠端更新，遠端標失效的曲目保留並標「已失效」；
   - 歌單名稱、描述、封面未在本地覆寫就跟遠端；
   - 任何一頁失敗或筆數不足時只新增與更新、不移除，並在歌單頁顯示「上次刷新：部分完成」；
   - 抓一頁寫一頁、每頁一個 transaction 加刷新代際，完整抓完後一次套用移除與順序；
   - 重新匯入同一張遠端歌單等於刷新，不覆寫本地設定（M12）。
3. **來源失效**：遠端 `NotFound` 或無權限時標「來源失效」、停止自動刷新、保留唯讀副本並提供「重試」。
   自動刷新不跳 toast，只更新歌單頁狀態（ADR 0013）。
4. **遠端操作**（插件 `libraryWrite`，只對已登入且具備能力的音源出現入口）：
   - 「從遠端歌單移除」有確認框，先寫遠端、成功後刪本地、再背景刷新，部分成功列出失敗項；
   - 「加入遠端歌單」在對話框勾選後直接送出，不重複加入已存在的曲目。
   
   本地「加入歌單」只列 `local` 歌單；匯入歌單的曲目不能在本地增刪或重排。
5. **僅元資料來源的匯入**（Spotify、QQ 等只有 `importPlaylist` 的插件）：逐首以共用評分核心在使用者設定的目標音源中搜尋，保留前 5 名、第一名自動選；
   匯入預覽頁可改選、重搜、排除；確認後建立 `local` 歌單並寫入 `match_results` 與 `track_origins`。自動匹配與手動重搜同一套評分。
   節流交給網路層的每插件限流（ADR 0013）。
6. **共用評分核心**（宿主 Dart，歌詞共用）：
   - 正規化：NFKC（`unorm_dart`）→ 小寫 → 繁簡統一（`opencc`）→ 去裝飾標點與空白 → 括號內容單獨比對；
   - 相似度用 `string_similarity`（Dice）；時長以「10 秒或 5% 取較寬」為硬門檻再連續給分；多歌手拆開取最佳；
   - 不使用播放量等來源特有訊號。

採用的慣例：Finamp 的 id 集合差集刷新；Namida 的「加入不確認、移除確認」；MusicBrainz 的標題延伸資訊（括號內容）不整段刪；
drift 官方的外鍵開啟方式；Unicode UAX #15 的 NFKC。

## 後果

- 好的：
  - 關聯由外鍵保證，孤兒清理不再誤刪；
  - 刷新結果可預期且部分失敗看得見；
  - 遠端失效有明確狀態；
  - 匯入與歌詞的匹配一致，手動重搜也有評分。
- 壞的：
  - 舊資料匯入要把整數陣列與反向欄位轉成關聯表，並換算覆寫旗標；
  - `opencc` 需要 native assets，要在各平台建置驗證。
- 之後要注意：來源失效時「另存為本地歌單」、曲目收藏、網易「疑似換版本」偵測列在功能凍結待辦；歌詞端如何使用評分核心由歌詞的 ADR 定。

## 如何確認

- 單元測試：
  - 刷新差異：新增、移除、順序、元資料、覆寫旗標、部分失敗不移除、重複影片保留、來源失效停止自動刷新、重新匯入不覆寫設定。
  - 評分核心：全半形、繁簡、括號、時長門檻、多歌手；自動與手動重搜同分。
- 資料庫測試：外鍵連帶刪除、孤兒清理只刪無人參照的曲目、刷新中途失敗後的一致性。
- 插件契約（ADR 0015）：`importPlaylist` 分頁與完整性回報、`libraryWrite` 的錯誤對應。
