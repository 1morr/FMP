> 一次性的發版評估，回答三個問題：從 v1.9.1 到現在改了什麼、這些改動是不是好的、
> 現在能不能發 v1.10.2。**它是審查記錄，依 `docs/README.md` 的規則不該長住在
> `docs/`**：v1.10.2 發布後刪掉，使用者要看的那半在 GitHub Releases 的 body 裡。
> 判斷的證據來源：三份 release notes、`git cherry`、2026-09-09 的變更審計（本機

## 0. 結論

**可以發 v1.10.2。** `main`（`1c074e82`）CI 綠燈、open PR 為零、最近 40 次 `main`
的 CI 只有 2026-09-08 一次失敗（那次是 #73 之前的格式問題，已修）。發版前要做的只有
§4 的四件事，其中兩件是把「預設會刪資料」與「預設會連網」寫進 release notes。

## 2. 三段各做了什麼

### 2.1 v1.10.0（2026-09-09）—— 播放層重寫回合

release notes 寫得完整，這裡只列骨架：

- **播放**：解析與開流有時間預算（T1/T2），卡住的緩衝有看門狗（T3）；gapless 改成
  後端持有下一首、控制器跟隨；輸出裝置失敗獨立分類、不再怪到歌曲頭上；佇列還原走同
  一條有預算的路徑（#54）。
- **錯誤文案**：例外先映射成人看得懂的訊息再到 UI；載入失敗與載入中分開。
- **電台**：與音樂播放器共用 chrome、系統媒體控制不再露出四個做不到的按鈕（#40）。
- **資料**：備份匯入全有或全無；schema 版本化（不再靠猜形狀）；log 落盤輪替；
  `flutter_secure_storage` 9 → 10（Android 憑證第一次啟動重新加密）。

### 2.2 v1.10.1（2026-09-10）—— 兩個 P1 加一批修正

12 個 fix：憑證庫讀不到時退成未登入而不是整個 app 每個請求都炸（#35、#89）、Netease
匿名 404 報成「需登入」而非 VIP（#87）、首頁排行列與收合導覽軌的溢出（#84、#85）、
Bilibili 風控退避與背景停輪詢（#95 的電台那半）、release notes 用 markdown 渲染（#82）、
設定放回導覽列（撤銷 v1.10.0 的一次「為規範而改」）。6 個依賴升級，其中 `just_audio`
0.9 → 0.10、`file_picker` 8 → 11、`tray_manager` 0.2 → 0.5 三個是大版本。

## 3. 是好的修改嗎

### 3.1 明確是好的（有 issue、有測試、有實機）

上表每一列，加上 v1.10.0 的播放預算／看門狗／gapless／輸出裝置分類與 v1.10.1 的憑證
庫降級。它們的共同點是：先有 repro（issue 或量測），修法有測試釘住，使用者可見的部分
在裝置上看過。這一輪 26 張 issue 關閉，沒有一張是「改了程式碼但沒驗證」關的。

### 3.2 好，但代價要讓使用者知道

| 改動 | 代價 | 該怎麼講 |
|---|---|---|
| 播放歷史上限預設 10,000 | **第一次播放時會刪掉超出的最舊紀錄，且無法復原**。歷史超過一萬筆的使用者會在不知情下失去資料 | release notes 的 Upgrading 段必須寫；想保留的人升級後先到設定改成 50,000 |
| 自動檢查更新預設開 | 啟動 8 秒後打一次 GitHub API | 一句話說明可在「關於」關掉 |
| `flutter_secure_storage` 10（v1.10.0 已發） | 降回 v1.9.1 要重新登入三個源 | v1.10.0 notes 已寫，v1.10.2 不必重講 |
| settings schema v3、備份 v5 | 降回 v1.10.1：設定列的版本號比舊 app 認得的大，舊 app 跳過遷移、忽略新欄位，不會壞；v5 備份檔在舊 app 會在預覽前被拒（設計如此） | 不必講，但要知道 |
| 縮圖檔位公式改了（#107） | 所有封面重新下載一次 | 一句話 |

### 3.4 目標沒達到的

- **M4 的行數出口**：音訊層加音源層要減 1,000 行，實際減 405；4.9 再做只減 11。原因寫
  在 `docs/plan.md` 的 4.9 那列：搬走的條件換回一個快照建構子加 23 格 switch。換到的
  是等價與可測性，不是行數。這是誠實的失敗，不是隱藏的。
- **#95 的 WBI 簽名**：量測顯示目前不驗簽，做了無法驗證，判定不做。若 Bilibili 開始
  驗簽，匿名播放會再壞一次 —— 到時 `_checkResponse` 的 dartdoc 有這次量測可對照。

### 3.5 沒有實機覆蓋的（發版前要知道，不是要補）

- 4.9 那輪的實機全走網易雲：這台機器 Bilibili 排行榜被 -352 風控、YouTube 要登入，
  所以那兩個源的串流路徑在事件路由改寫後沒有裝置驗證，只有測試。
- 播放歷史上限「真的刪最舊」只有倉庫測試。
- `audio_session` 0.2.4 的 transient duck 與 becoming-noisy 在模擬器上發不出事件，
  只驗到來電中斷。
- 帳號失效三態只在 Android 看過，Windows 未實測。
- #82（更新對話框的 markdown 渲染）要等 v1.10.2 發出去，在裝置上真的收到一次更新
  才驗得到。

## 4. 發版前的四件事

1. **Release notes**：workflow 會依 Conventional Commits 自動分組，但 §3.2 的前兩項
   要人手加一段 Upgrading（歷史上限會刪資料、自動檢查更新可關）。Release 建出來是
   草稿，按 Publish 之前改。
2. **tag**：`git tag v1.10.2 && git push origin v1.10.2`。
3. **發完補版本號**：`pubspec.yaml` 的 `version` 改成 `1.10.2+1010002` 並 commit
   （`pubspec_version_test.dart` 守著，忘了下一次 CI 會紅）。
4. **發完驗 #82**：在裝置上收到 v1.10.2 的更新對話框，確認 release notes 不再是純
   文字，然後關 issue。
