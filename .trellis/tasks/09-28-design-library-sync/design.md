# 設計：音樂庫與同步

## 1. 資料模型（drift，ADR 0010）

| 表 | 重點欄位 | 備註 |
|---|---|---|
| `playlists` | id、`kind`（`local`／`imported`／`mix`）、名稱、描述、封面、排序 | 名稱不再唯一（舊版重名自動加「(2)」不帶過去） |
| `playlist_remote` | 歌單 id（FK）、插件 id、遠端歌單 id、擁有者、`name_overridden`／`description_overridden`／`cover_overridden`、上次刷新時間與結果、狀態（正常／來源失效） | 只有 `imported` 有這一列 |
| `playlist_entries` | 歌單 id（FK，刪歌單時連帶刪）、位置、曲目鍵（FK）、遠端項目 id（可空） | **不對（歌單, 曲目鍵）設唯一**：YouTube 歌單可含重複影片 |
| `tracks` | 曲目鍵（ADR 0005 的 `TrackKey` 格式，照搬）、標題、歌手、時長、封面清單、可用狀態與原因 | 同一首歌只有一列 |
| `track_origins` | 曲目鍵、原始平台、原始 id | Spotify／QQ 匯入時記下，供歌詞直取與重新匹配 |
| `match_results` | 原始曲目、選定的曲目鍵、分數、`user_selected` | 匹配結果持久化，使用者改選後不再重算（ADR 0014） |

- 開啟資料庫時 `PRAGMA foreign_keys = ON`（drift 官方建議，migration 期間關閉再開）。
- **孤兒清理**：以 SQL 找出沒有被任何 `playlist_entries`、佇列、下載紀錄參照的曲目，登記在啟動維護清單（ADR 0017）。
  靠外鍵與查詢判斷，不再依手動維護的反向欄位（舊版遺失資料的原因）。播放歷史存快照、不參照曲目列，不影響清理。
- 舊資料匯入（ADR 0010）把 `trackIds`／`playlistInfo` 轉成 `playlist_entries`；舊歌單的本地改名、自訂封面換算成對應的 `*_overridden` 旗標。

## 2. 匯入與刷新（遠端為權威、只往下）

- 匯入與刷新都經插件 `importPlaylist`（取完整清單，可分頁）；刷新由 ADR 0017 的排程器或手動觸發。是否帶登入依 ADR 0012 的音源設定。
- 差異處理（已決定 A）：
  1. 依曲目鍵比對：遠端有、本地沒有 → 新增；本地有、遠端沒有 → **從這張歌單移除**（曲目列留著給其他歌單、下載、佇列用，沒人參照時由孤兒清理處理；下載檔不刪）。
  2. 順序完全照遠端。
  3. 曲目元資料（標題、歌手、時長、封面、可用狀態）照遠端更新。遠端標成失效的曲目保留並標「已失效」（ADR 0013 的 `Unavailable`）。
  4. 歌單的名稱、描述、封面：沒有在本地改過（`*_overridden` 為否）就跟遠端；改過就保留本地值。
- **部分失敗**：任何一頁抓取失敗或筆數不足，就只新增與更新、不移除，並記錄「上次刷新：部分完成」顯示在歌單頁；下次完整刷新時再處理移除。
- **寫入方式**：抓一頁寫一頁，每頁一個 transaction，整輪用刷新代際標記；完整抓完後以一個 transaction 套用移除與最終順序。中途失敗不會留下半套順序。
- **遠端歌單失效**（`NotFound`、無權限）：狀態標成「來源失效」並停止自動刷新，保留本地副本唯讀可播；歌單頁顯示原因與「重試」。不再每次排程都重試並跳錯誤。
- 刷新結果：手動刷新顯示新增／移除／更新數；自動刷新不跳 toast，只更新歌單頁的「上次刷新」狀態（ADR 0013「背景工作不跳 toast」）。
- 重新匯入同一張遠端歌單＝刷新，不覆寫本地設定（M12）。

## 3. 遠端操作（B1、B2、E7）

- 經插件 `libraryWrite` 能力；只有登入且具備該能力的音源才出現入口（ADR 0014 能力驅動 UI）。
- **B1 從遠端歌單移除**：確認框（說明「同時從本地歌單移除」），先寫遠端、成功後刪本地對應項目，再背景刷新該歌單。部分成功時列出失敗項目。
- **B2 加入遠端歌單**：對話框勾選目標歌單後送出，**不另加確認框**（勾選本身就是明確操作；Namida 慣例：加入不確認、移除才確認）。
  已在遠端的曲目不重複加入；未登入的音源不列出並提示；成功後背景刷新對應的匯入歌單。
- 本地「加入歌單」只列 `local` 歌單；匯入歌單的曲目在本地不能增刪、不能重排（B1／B2）。

## 4. 僅元資料來源的匯入與匹配（E5）

- Spotify、QQ 等是具備 `importPlaylist`、沒有 `resolveStream` 的插件；匯入後逐首用**共用匹配評分核心**（ADR 0014 決定 9，與歌詞共用）在使用者設定的目標音源中搜尋。
- 評分核心（宿主，Dart）：
  - 正規化：NFKC（`unorm_dart`）→ 小寫 → 繁簡統一（`opencc`）→ 去裝飾標點與空白 → 括號內容（Live、Remix、feat.）抽出單獨比對，不整段刪。
  - 相似度：`string_similarity`（Dice）；時長硬門檻「10 秒或 5% 取較寬」再連續給分；多歌手拆開比對取最佳。
  - 播放量等來源特有訊號不進核心（插件不回報就沒有），避免偏向特定音源。
- 自動匹配與手動重搜走**同一個**評分（舊版手動重搜只看播放量）。每首保留前 5 名候選；第一名自動選定。
- 匯入預覽頁（沿用）：已匹配可展開候選改選，未匹配集中顯示可重搜，可排除；確認後建立 `local` 歌單並寫入 `match_results` 與 `track_origins`。
- 匹配失敗的曲目保留在預覽的「未匹配」區；使用者不處理就不加入歌單。錯誤依 ADR 0013 呈現，不再一律「發生錯誤」。
- 搜尋節流交給網路層的每插件限流（ADR 0013），不再寫死 800／1000ms 延遲。

## 5. 待辦（功能凍結，第 20 項）

- 來源失效的匯入歌單「另存為本地歌單」、曲目層的收藏／喜歡、「疑似換版本」偵測（網易新舊 song id）——都是新功能。

## 6. 閘門

- 單元測試（差異處理）：新增、移除、順序、元資料更新、覆寫旗標、部分失敗不移除、重複影片保留、來源失效停止自動刷新、重新匯入不覆寫設定。
- 資料庫測試：外鍵連帶刪除、孤兒清理只刪無人參照的曲目、刷新中途失敗後的一致性。
- 評分核心：正規化管線（全半形、繁簡、括號）、時長門檻、多歌手；自動與手動重搜同分。歌詞端（第 15 項）共用同一組測試。
- 插件契約（ADR 0015）：`importPlaylist` 分頁與完整性回報、`libraryWrite` 的錯誤對應。
