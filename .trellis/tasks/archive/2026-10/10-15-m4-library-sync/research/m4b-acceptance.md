# M4b 驗收：兩平台端到端

來源：`implement.md`「## M4b 驗收」→「### 兩平台端到端」的六個步驟。

- **日期與版本**：2026-10-21，FMP `main` e93a8382；fmp-plugins `main`（spotify 1.0.0、qqmusic 1.0.0、bilibili 1.10.0、netease 1.7.0、youtube 1.6.0）；dev flavor、debug build。
- **Android**：模擬器 `Medium_Phone`，App 語系英文；沿用 M4a 驗收後的開發資料，三個平台的登入都在，但這次驗收沒有用到登入。
- **Windows**：只做第 5 步，見下面。
- **擁有者不在場**：六個步驟都不需要登入或遠端寫入。
- **平台**：照 M4a 驗收的擁有者決定，沒有平台差異的步驟只做 Android。第 1–4、6 步都是共用的 Dart 程式碼；第 5 步的檔案對話框與重啟是平台各自的實作，兩個平台都做。

## 結果

| 步驟 | Android | Windows | 模式 |
|---|---|---|---|
| 1 Spotify、QQ 各匯入一張 → 改選、重搜、排除 → 建立 → 播一首 | 通過 | 不做（共用程式碼） | 真實、匿名 |
| 2 同一張再匯入：沿用、沒有搜尋 | 通過（見觀察 2） | 不做 | 真實、匿名（只讀歌單） |
| 3 匹配目標拿掉網易、調順序 → 重搜看到變化 | 通過 | 不做 | 真實、匿名 |
| 4 首頁排行 → 探索 → 多選加入歌單 → 停用榜單 → 間隔關閉再改回 | 通過 | 不做 | 真實、匿名 |
| 5 備份：匯出 → 另一平台還原 → 登入保留、確認框、自動備份 | 通過（#303 合併前，見下） | 通過（同左） | 重播（`fmp-test` 假登入） |

## 各步驟的觀察

### 1. 匯入兩張外部歌單

- **設定**：匹配目標只勾網易、YouTube（這個順序），B 站與 `fmp-test` 不勾，壓低請求量。
- **Spotify「Top 50 - Global」**（`37i9dQZEVXbMDoHDwVN2tF`，50 首）：
  - 讀取時 14 首沿用了 PR 19 實機時 Today's Top Hits 的結果（同一首歌的 Spotify id 相同就沿用，跨歌單也一樣）。
  - 「開始匹配」：其餘 36 首在網易、YouTube 各搜一次，50 首全部匹配到，約 20 秒。
  - 改選：「the cure」的前 5 名有 4 個網易版本、1 個 YouTube Lyric Video，都是 100%；改選 YouTube 那個。
  - 重搜：「Stop The Wedding!」以自訂關鍵字 `Ashe Stop The Wedding official audio` 重搜，候選換成以 YouTube 為主的一批。
  - 排除：「Nicole Kidman」。底部顯示「1 首不會加入」。
  - 建立：「本機 · 49 首」，開出新歌單的詳情。
  - 播放：點第一首（YouTube）：`Track audible`，`sinceRequestMs` 4121；媒體工作階段 `PLAYING`，之後暫停。
- **QQ**：
  - 先開的 `8407701300` 有 203 首，兩個目標要約 400 次搜尋，不符合「只做最少的操作」，沒按「開始匹配」就離開，沒有確認框，也沒有發出搜尋。
  - 改用 PR 19 實機用過的 `9780162922`（15 首），15 首都沿用先前的結果。
  - 重搜：「那页夏天」原本沿用的是網易上別人翻唱的版本（67%，見觀察 3）。重搜後自動選中 YouTube 上王俊凯的原唱（99%）。
  - 改選：同一首改成第三名。
  - 排除：「大概」。
  - 建立：「本機 · 12 首」。
  - 播放：一首網易：`Track audible`，`sinceRequestMs` 2500，`PLAYING`。

### 2. 同一張再匯入

- Spotify 同一張再匯入：
  - 第一次：49 首沿用，「Man I Need」顯示等待中。
  - 退出再匯入：50 首全部沿用，讀完直接完成，沒有「開始匹配」也沒有搜尋請求，只有讀歌單的 1 個 embed 請求。
- 原因：
  - 資料庫裡 `Man I Need` 的 `origin_id` 與當下 embed 頁的 id 相同（`1qbmS6ep2hbBRaEZFpn7BX`），FMP 的查詢與比對沒有問題。
  - 這是 Spotify 的 embed 頁偶爾給同一首歌另一個曲目 id，第 3 步也遇到一次（「Wonderwall - Remastered」）。
  - 結果只是那一首多搜一次，記為觀察，不修。
- 為了確認原因，我直接對 Spotify 的 embed 頁發了 1 個匿名 GET（不經 App）。

### 3. 匹配目標的設定

- **操作**：設定「音樂庫」的匹配目標取消網易，勾 B 站，拖曳成 B 站、YouTube。
- **結果**：再匯入 Spotify 那張：
  - 讀取時有 1 首沒沿用（觀察 2 的 id 變動，這次是「Wonderwall - Remastered」）。
  - 它只在 B 站、YouTube 各搜一次（`search/type` 1、`youtubei/v1/search` 1），**沒有網易的請求**。
  - 結果選中 B 站的版本（100%）：與 YouTube 同分時，照設定的順序取 B 站。
- **一次誤操作**：首頁排行的 YouTube「本週新歌」一度變成未勾。
  - 原因：從預覽頁回到設定分頁時，它還停在「音樂庫」子頁，我原本要點進「音樂庫」的那一下，落在子頁上「本週新歌」的位置。
  - 驗證：勾回後反覆切換匹配目標、拖曳，排行設定都不受影響，所以不是 App 的問題。

### 4. 首頁排行與探索

- **首頁**：B 站「音樂排行榜」、`fmp-test` 的 Hot／New／Broken、網易「熱歌榜」、YouTube「本週新歌」，各有「更新於」。`fmp-test` 的 Broken 顯示「更新失敗」。
- **探索與多選**：B 站榜單的「查看全部」→ 探索頁有 6 個分頁 → 長按第 2 首進入多選，再勾第 3 首 →「加入歌單…」→「Acceptance」：提示 `Added to "Acceptance"`。
- **停用**：設定取消網易「熱歌榜」：
  - 快取庫 `cache_entries` 的 `chart:netease:hot` 立即刪掉，其餘 4 列還在。
  - 首頁不再有網易的榜單。
  - 這也補上 `m4-adr-tests.md` 的缺口 2。
- **間隔**：「首頁排行」間隔改成「關閉」，再改回 60 分鐘：都沒有觸發抓取（上次成功在一小時內）。
- **間隔關閉時只能手動**：改成「關閉」，在探索頁按「重新整理」，仍會抓一次（B 站 `ranking/v2` 1 個，`Chart refresh finished {succeeded: 1}`）。之後改回 60 分鐘。

### 5. 備份

這一步沒有在 `main` e93a8382 上重做，用的是 #303 合併前、同一天（2026-10-21）的兩平台實機，紀錄在 #303 描述的「實機」段。

- **差異**：那次之後只改了兩件事：
  - 無法使用的插件，連同它的每音源設定與榜單設定一起刪；
  - 一個回歸測試的竄改斷言。
- 兩者都不在這一步走的路徑上，所以沒有重做。
- 那次的結果：
  - **Windows → Android**：還原後 Windows 的歌單在，`fmp-test` 仍登入；這台原本的帳號列都在，`plugin_storage` 是空的；`backups/` 有還原前的自動備份。
  - **Android → Windows**：Windows 自己重啟；只在 Windows 上的歌單消失，`fmp-test` 仍登入，Android 的其他帳號沒有跟過來。
  - **確認框**：列出插件與網域，加上警告。
  - **較新版**：`user_version` 99 的檔被拒，資料不變。
  - **Debug 頁**：「從備份還原」走同一條路。

### 6. 離線

做法是 `svc wifi disable`、`svc data disable`。

- **首頁**：頂端「No network connection」。有快取的榜單照常顯示，各有「更新於」。
- **沒有快取的榜單**：在離線時把網易「熱歌榜」勾回來（快取在第 4 步已刪）。
  - 首頁那一塊顯示「No network connection／Connect to a network and try again.」；
  - 探索頁的「熱歌榜 · 網易雲音樂」分頁顯示同樣的離線空狀態。
  - 這補上 `m4-adr-tests.md` 的缺口 1（探索頁）。
- **恢復網路**：約 1 秒內，網易「熱歌榜」自動補抓（`Chart refresh finished {pluginId: netease, succeeded: 1}`），這是 PR 21 的「缺快取就立即到期」。

## 觀察與後續

1. **自動選中翻唱**：標題（0.6）加時長（0.1）就有 0.7，超過 0.6 的門檻，歌手完全對不上也會自動選中。
   - 實例：QQ「那页夏天」（王俊凯）在只搜網易時選中別人翻唱的版本（67%）；網易上沒有原唱。
   - 加 YouTube 重搜後選中原唱（99%）。
   - 這是 PR 16 的設計（ADR 0019 §決定 5 的權重與門檻）。要不要對「歌手完全不符」降分或提高門檻，由擁有者決定。
2. **Spotify 的曲目 id 偶爾會變**：同一首歌在不同次讀取給出不同的 id，沿用就會漏掉那一首、多搜一次。影響小，不修。
3. **大歌單的請求量**：QQ 203 首、兩個目標約 400 次搜尋。現在沒有確認或上限，交給每插件限流。
   - 預覽頁在開始前已顯示「每首會在 n 個音源搜尋」，使用者可以先減少目標。
   - 是否需要「超過 n 首時提醒」由擁有者決定。
4. **其餘後續**：`implement.md`「PR 19 → 之後」「PR 22 → 之後」的項目都還在，這次驗收沒有新增程式碼問題。

## 最終確認（2026-10-22，擁有者委託）

驗收後補做了兩項後續：#305（同文字歌手衝突不自動選、大量搜尋前確認）、#306（插件與插件庫不一致的提示、「以登入身分瀏覽」留在這台）。擁有者回覆「你試完通過就可以了」，由主對話在合併後的 `main` a71866f1 上確認：

- **平台**：Android 模擬器 `Medium_Phone`、dev flavor、debug build；沿用上面的開發資料。Windows 沒做：兩個 PR 只改共用 Dart。
- **觀察 1 的實例（離線）**：「那页夏天」的兩個真實候選取自模擬器的 `tracks` 表，以 `main` 的評分核心重算：
  - 網易上另一位歌手的同名歌：67%、歌手分 0、`artistConflict` 真 → 不自動選（之前會自動選）。
  - YouTube 上王俊凯的原唱：96% → 自動選。
- **備份與還原（重播，沒有網路請求）**：
  - 匯出：存到 Downloads。備份檔的 `source_settings.browse_as_logged_in` 全是空的。
  - 這台的值：B 站、網易、YouTube 都是 0（關）。
  - 還原同一份：確認框列出插件與網域，按下後 App 照設計關閉；`backups/` 多一份還原前的自動備份。
  - 還原後：三個插件的值仍是 0；歌單 18 張、帳號列 4 個、插件 7 個；`integrity_check` ok。重開沒有錯誤。
- **插件頁（真實，在 #306 的分支上）**：讀官方 index 2 次。B 站 1.10.0、網易 1.7.0、YouTube 1.6.0 與 index 同版本，走 SHA-256 比對，沒有被標「與插件庫不一致」。
- **收尾**：讀取的資料庫副本已刪；匯出的備份檔已從模擬器刪除；模擬器已關。

結論：M4b 通過。
